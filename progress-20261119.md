- **`P_NULL` = 0.30, fixed** (agreed range 25–30%). Not a calibration knob, because it
  changes the score's composition rather than item difficulty.
- **Splits:** dev 50, test 200 (attempt-cap exclusions are not backfilled).
- **Calibration:**
  - only generation knobs move, never items;
  - dev only, at most 3 rounds;

  the probe cap (B2-Q9).

## C0.1: versioned generation presets (refactor only)

**Summary.** The sampling ranges (`presets.py`) and labeller constants (`label.py`) move
into a frozen `presets.Preset` dataclass. `P01` holds the 0.1 values, and `PRESETS` maps
names to presets.
- The preset is a required keyword argument of `items.sample_item`,
  `label.evidence`/`label_runs`, `confusers.check_item` and `pipeline.label_indices`.
- Worker processes receive the preset's name and look it up in `PRESETS`, because a
  `MappingProxyType` field does not pickle. `label_indices` refuses a preset that is not
  registered.
- `scripts/label_items.py`, `audit_items.py`, `ramp_sweep.py` and `gb2_sweep.py` pass
  `P01` explicitly. No CLI change: a `--preset` flag arrives with P02.

**Decisions:**
- **Plant constants are not in the preset.** Sensor and load noise, drum model, three-element
  control, day length and rated MW are hotwell configuration copied from v0.4.0 and
  shared by every preset. `check_upstream_copies.py` still checks them as module
  constants.
- **The builder does not take a preset.** Plan §4 said "sampler, builder and labeller",
  but `build.py` reads only plant constants. Everything it builds comes from the
  `ItemRecord`, so passing a preset to it would be unused.
- **No default preset.** A default would let 0.2 code silently generate 0.1 items.
- **`SENSOR_BIAS_X` removed.** It was an unused alias of `MAG_RANGE`. Its meaning
  (sensor bias = ratio × D_i) is now documented on `Preset.mag_range`.

## C0.2: master seed from a file in label_items.py

**Summary.** `scripts/label_items.py` takes the seed from `--master N` or from
`--master-seed-file PATH`; exactly one is required. `--split test` refuses `--master`,
because a seed on the command line is visible to anything that lists processes (the
progress-20261108.md incident).
- The file format is the one `package_split.py` reads: one non-negative integer,
  surrounding whitespace allowed.
- `read_seed` rejects anything else without echoing the file's content.
- `run.json` still records only the seed's SHA-256.

**Decision.** `--master` stays for dev, whose seed (20261107) is public and appears in
the 0.1 docs. The dev commands in the logs keep working.

## C0.3: per-item retry pipelining in label_indices

**Summary.** `pipeline.label_indices` runs everything in one spawn-context process pool and
advances each item as soon as its own previous step finishes: faulted run, then twin
run, then label (in the main process), then the next attempt's faulted run, the
confuser check, or done. 0.1 ran barrier-synchronized rounds, with all faulted runs,
then all twins, then labels, then the next attempt, and confusers last.
- The returned dict is sorted by index.
- The progress lines now carry elapsed time, and a final `== done` line gives run
  counts.
- `run_items` is unchanged; the sweep scripts still use it.

**Why the results cannot depend on the schedule.** Each index's attempts stay
sequential, and every run is a pure function of its item record (cache-keyed). One
consequence: the order of entries in the in-memory results dict changes, so it is
sorted by index. The label files were written per index before and still are.

**Verification:**
- **Old against new**, same short configuration: dev master 20261107, indices 0–15,
  `cap=3`, `until=10800`, 4 workers, separate caches.
  - Old: a clean worktree at 719a1ef, whose pipeline code is the same as 0826db8.
  - New: this tree. Harness script in the session scratchpad.
  - The runs covered 39 faulted and 39 twin runs, regenerations, 10 exclusions at the
    cap and 3 confuser checks.
  - Results: `diff -r old/labels new/labels` is empty (16 files), and the `summarize()`
    tables are identical.
- **Wall time:** new 2035 s against old 2179 s. Both ran concurrently with each other
  and with the 28-worker G-B0r regeneration, so this is not a speed measurement.
- **First attempt failed in my harness:** a `BrokenProcessPool` in both old and new
